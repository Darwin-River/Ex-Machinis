# Game engine sources

The C sources of the `game-engine` and `events-engine` (see [the engine's README](../README.md)).

```sh
make all     # builds bin/game-engine, bin/events-engine, bin/lua-check and eforth.blk
make test    # unit tests, link-check, and checks the Lua library, examples, manual and blog code all compile
make link-check  # links every object of both engines into one program, to prove no names clash
```

- `lua_drone.c`, `lua_library.c`, `lua_library.lua`: how a drone's Lua program runs, and the game functions it can call (listed in [lua-functions.md](../../documents/lua-functions.md)).
- `engine.c`, `main.c`: the game engine's loop; `engine_e.c`, `main_e.c`, `event*.c`: the events engine. Where its names would clash with the game engine's they carry an `ee_` prefix (`ee_init`, `ee_pass`, `ee_run`, `db_e.h`), so both can link into one program (#694 stage 4); `ee_bindings.c` gives the shared modules its trace and database connection in `bin/events-engine`.
- `settle.c`, `settle_clock.c`, `ee_embed.h`: with `EVENTS_IN_ENGINE=1` (default 0), shard 0's game engine settles events between turns by running `ee_pass` on a second database connection of its own, under the events engine's lock, and `bin/events-engine` rests (#694 stage 4 step 2). While a pass runs, `engine_get_db_connection()` returns the settlement connection and log lines start `[events]`. `settle_clock.c` says when a pass is due: about every 50 ms, at once after a full batch, and never so often that turns starve (`test_settle_clock.c`).
- `event_heap.c`: with `EVENT_HEAP=1` as well (default 0; it needs `EVENTS_IN_ENGINE=1`), settlement takes due events from a min-heap in memory keyed as the batch query's `ORDER BY` (game_t, action, id), not from that query (#694 stage 4 step 3, #432). `db_e.c` loads it at the first pass, reads a batch's rows by id, drops events no longer pending and puts back those still pending after the batch; `db_insert_event` and `db_insert_event_e` stage the events they insert and the heap takes them when the connection commits; each pass reads the ids past the highest seen and the ids it skipped (not committed yet; a skip of over 256 ids as a range) for 10 s, a sweep each second the ids of the last 10-20 s, and a full check every five minutes of the ids up to the highest seen (#946), so what other shards insert gets in too (`test_event_heap.c`).
- `wake_heap.c`, `db_wake.c`: with `WAKE_HEAP=1` (default 0; needs nothing else), each game engine keeps its shard's commands in memory (#694 stage 4 step 4, #432): waiting by due time, then ready in the batch queries' order (station drones', loading drones' but their resumes, the rest; each by id). `db_wake.c` makes each batch from there, checking a chunk of ready commands with one query by id under the queries' own conditions; a resume held for its drone's action waits until the action's next pending event is due, then only that action is asked about each batch until it is done. It loads at the first batch; the engine's own writes to `commands` are staged and applied when their transaction commits; each batch reads the ids past the highest seen, then the ids that read skipped (not committed yet) for 10 s, so a drone's commands come in id order (a release's script before its `<launched>`), and the untimed commands; each second a sweep of the last 10-20 s, and a full check every five minutes (`test_wake_heap.c`; `game-engine/tools/release-order-check.sh` checks the order on a load world).
- `holding_state.c`, `db_state.c`: with `MEMORY_STATE=1` (default 0; needs nothing else), each game engine keeps a copy of `holdings` in memory and answers `units()` (query 212) from it (#694 stage 4 step 5, #431). Triggers on `holdings` write every change, whoever makes it, to `holding_changes` (migration 0092), in the writer's transaction; the engine turns that feed on at start (shard 0 with the flag off turns it off and empties it). It loads the table at the first chance between turns; a turn's transaction reads the feed's new ids (and the ids an earlier read skipped, for 60 s) at its first `units()`, or, in one engine that settles itself (`EVENTS_IN_ENGINE=1`, one shard), only after a settlement pass; every engine reads it once a real second. A change applies to its row only over an older one. Every five minutes the table is read again in a snapshot with the feed, with a WARNING if any row differed; a NOTICE each minute gives the counts; shard 0 deletes changes over two real minutes old. `MEMORY_STATE_CHECK=1` asks MySQL each `units()` too and logs any difference (`test_holding_state.c`).
- `event_ids.c`, `db_reserve_event_ids` (`db_common.c`): with `ENGINE_OWNS_EVENTS=1` (default 0; needs nothing else), the engine takes its events' ids itself (#694 stage 4 step 6). A turn (`protocol_flush_events`, after its order locks and delay) and settlement's follow-ups (`db_insert_event_e`, the fuel refund) reserve ids from the `events` table's own AUTO_INCREMENT counter: placeholder rows inserted and rolled back on a connection of the reservations' own (READ COMMITTED: under REPEATABLE READ a rolled-back insert leaves gap locks on the end of the table), then the events are inserted with those ids. Every other writer keeps AUTO_INCREMENT and always gets higher ids, so each drone's events keep the id order they had. A NOTICE each minute gives the counts; a failed reservation falls back to AUTO_INCREMENT. `make CHECK_EVENT_IDS=1` builds a check that the placeholders' ids were consecutive and that no event of the drone already had a higher id (`test_event_ids.c`).
- `protocol.c`, `shares.c`, `station.c`, `crash.c`, `orbits.c`, `game_time.c`: the game's rules.
- `embed/`, `embed*.c`: the FORTH VM for drones released before FORTH was retired ([its own MIT licence](embed/LICENSE)).
